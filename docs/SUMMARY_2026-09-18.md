## 2. Three corrections from Andres that changed the design

These are worth re-reading before extending anything, because in each case the tool
was confidently wrong and the data agreed with him immediately.

**Sneasler and Rillaboom are not a coincidence.** Species-level lift reported 1.03,
i.e. chance. Conditioned on the item: Grassy Seed Sneasler runs Rillaboom **99%** of
the time, Psychic Seed runs Indeedee **100%**. Unburden plus a terrain seed, two
mutually exclusive builds wanting opposite partners, cancelling to nothing when
averaged. This produced the item-conditioned cores view, and the lesson generalises:
**a species is not always one thing.**

**"What you would lose by removing each Pokémon" was lying.** It measured unique
super-effective coverage and was labelled as though it measured everything. Indeedee
scored zero while holding the team together through terrain. Renaming is mandatory;
modelling the interactions is not, and is argued against below.

**Weather belongs in the damage calculator.** Pelipper's rain takes a Fire hit on
Golisopod-Mega from 4x to 2x. That is a damage-threshold effect, invisible to
correlation, and it is what pushed the calculator up the order.

**A** is the highest-value hour available. The tab has the right content in the wrong

**B** is the Indeedee fix. Not by modelling terrain and enablement — by measuring

builds are essentially never seen without this one. It would catch Indeedee via
Psychic Seed Sneasler at 100%, and it never invents a mechanic. Its honest limit is
that it detects correlation in how people build, so it would miss an interaction
nobody has discovered yet.

### Explicitly not doing

**Modelling battle interactions as an enablement graph** — terrain setters activating
seeds activating abilities. Showdown implements these as event callbacks, not data, so
extracting them is program analysis rather than a transform. This project already paid
that cost at tiny scale: four retyping abilities are hardcoded in `typechart.py` for
exactly this reason. A model covering six interactions and silently missing the
seventh is worse than none, because you would stop double-checking it. Where more
depth is needed, the damage calculator with explicit, visible field toggles is the
honest route.

Also still out: ML of any kind, replay parsing, bring-4 (belongs to VFC xV).

## 5. The team editor question

Andres asked whether an in-app editor would beat the damage calculator. It is now the
strongest remaining item, for one reason: **`load_paste.py` needs network**, so
teambuilding is impossible on a plane. The tool is a reference offline, not a loop.

The architectural decision to make deliberately: the app is strictly read-only, and
`DECISIONS` backs that with a real reason — DuckDB allows one writer and VFC xV reads
the same file. Preferred order:

1. **Session-state only.** All visuals already take `team` and `formes` as arguments,
   so they need no change. Zero writes, zero lock. A browser refresh loses the draft.
2. **Plus a drafts file** under `data/drafts/`, separate from the warehouse. Persists
   without taking the DuckDB write lock. Deserves its own logged decision.
3. Writing to `my_team` — avoid; it is the only option that can break xV.

The cheap path: **the swap view already is a minimal editor.** Adding "apply this
swap" to session state delivers most of the loop without a full set editor, which is
where the validation complexity lives.
